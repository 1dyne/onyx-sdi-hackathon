# Onyx SDI — Smart Drill Indicator

족저압(FSR 4채널) + IMU 데이터를 양발 동시에 받아 실시간으로 보여주는 웨어러블 대시보드입니다.
설치가 필요 없는 PWA로, 브라우저에서 바로 BLE 유닛에 연결합니다.

**라이브 데모 → https://1dyne.github.io/onyx-sdi-hackathon/**

> Web Bluetooth가 필요합니다. 데스크톱/안드로이드 Chrome·Edge에서 동작하며, iOS Safari는 지원하지 않습니다.
> 하드웨어가 없어도 CONFIG → DEMO 모드로 전체 UI를 시연할 수 있습니다.

---

## 무엇을 하는 물건인가

훈련 동작(drill)을 미리 정의해두고, 착용자가 그 동작을 수행하는 동안 발바닥 4개 지점의 압력과
발의 기울기(roll/pitch/yaw)를 10Hz로 읽어 실시간 판정합니다.

- **LIVE** — 좌우 실루엣에 압력 분포를 그리고, 동작 품질을 즉시 판정
- **TRAINING** — 정의된 drill 실행, 세션 기록
- **CONFIG** — drill 편집, ADC/IMU 보정, BLE 옵션
- **LOG** — 세션 히스토리와 RAW 모니터

### 설계에서 중요한 부분

**양발이 완전히 독립적입니다.** 연결 상태·수신 버퍼·재연결 타이머가 발마다 따로 존재해서,
한쪽이 끊겨도 다른 쪽 스트림이 오염되지 않습니다. 한쪽만 연결해도 좌우 비교 위젯을 제외한
모든 기능이 정상 동작합니다.

수신 버퍼를 공유하지 않는 것이 핵심입니다 — BLE notification은 약 20바이트씩 쪼개져 도착하므로
38자짜리 샘플 한 줄이 여러 이벤트에 걸칩니다. 두 기기가 한 버퍼에 쓰면 줄 중간에서 섞여 양쪽 다 깨집니다.

## 오늘 작업 범위 (해커톤)

이 리포는 진행 중이던 프로젝트의 오늘자 스냅샷이며, 오늘 한 작업은 **BLE 연결 실패 수정**입니다.

증상은 대시보드에서만 연결이 실패하는 것이었습니다. 같은 노트북·같은 브라우저·같은 보드에서
콘솔로 직접 `getPrimaryService()`를 호출하면 10Hz로 완벽하게 수신되는데,
앱을 통하면 `NetworkError: GATT Server is disconnected`가 났습니다.
즉 UUID·펌웨어·브라우저는 모두 정상이고 연결 절차에만 문제가 있었습니다.

원인과 수정:

| # | 문제 | 수정 |
|---|---|---|
| 1 | Windows Chrome에서 `gatt.connect()` 직후 즉시 서비스를 탐색하면 실패하는 레이스 컨디션 | 연결 후 200ms settle, attach 전체를 3회 재시도(간격 300ms)로 감쌈 |
| 2 | 1차 탐색 실패 후 fallback이 이미 끊긴 GATT를 그대로 탐색해 2차 에러가 원인을 덮음 | fallback 진입 전 재연결, 실패 시 1·2차 에러를 함께 보존 |
| 3 | `gattserverdisconnected` 핸들러가 연결할 때마다 중복 등록 | 안정 참조로 교체 — 병렬 재연결 체인이 원천 차단 |
| 4 | 죽은 시도의 재연결 타이머가 새 연결에 끼어듦 | `releaseDevice()`로 타이머·리스너·기기를 먼저 회수 |
| 5 | 데이터가 한 줄도 안 오는데 배지가 "연결됨"으로 표시 | GATT 연결과 데이터 수신을 분리 — 2초 내 첫 notify가 없으면 `no-data` |

3번과 4번은 증상 리포트에 없던 것으로, 원인 추적 중에 발견해 같이 고쳤습니다.
반복 클릭할수록 상황이 나빠지던 이유였습니다.

수신 경로(`parseLine` / `onRx` / `dispatch`)는 검증이 끝난 코드라 한 줄도 건드리지 않았습니다.
첫 notify 감지는 같은 characteristic에 리스너를 하나 더 붙여서 처리하고, 첫 발화 후 스스로 해제합니다.

## 데이터 규약

Nordic UART Service (NUS) 고정:

| | UUID |
|---|---|
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| RX (notify) | `6e400003-b5a3-f393-e0a9-e50e24dcca9e` |

페이로드는 개행으로 끝나는 CSV 한 줄, 10Hz:

```
fsr1,fsr2,fsr3,fsr4,roll,pitch,yaw\n
```

예: `88,90,120,95,0.00,0.00,0.00`

FSR은 0–1023(10-bit), 각도는 도(degree)입니다. 4필드(FSR only) 레거시 형식도 받습니다.
12-bit로 출력하는 유닛은 CONFIG에서 ADC 최대값만 4095로 바꾸면 자동 환산되므로 펌웨어를 다시 굽지 않아도 됩니다.

두 유닛(ESP32 / nRF52840)이 동일한 프로필과 페이로드를 쓰기 때문에, 좌우 구분은
**사용자가 어느 버튼을 눌렀는지**로만 결정됩니다. 기기 이름으로 추론하지 않습니다.

## 세션 원시 기록 (v2.4)

세션 로그에는 집계값 외에 **10Hz 원시 스트림**이 함께 저장됩니다.
contact time, 보행 위상 분석, 연속 동작 인식은 전부 이 블록에서 계산합니다.

```jsonc
{
  "sessionId": "s_20260905_12345",
  "quality": 74, "duration": 180,        // 집계값 (기존)
  "byFoot": { "left": { "rawCount": 1800, "rawTruncated": false }, ... },

  "raw": {
    "schema": 1,
    "hz": 10,
    "startedAt": 1757000000000,          // epoch ms
    "fields": ["t","fsr1","fsr2","fsr3","fsr4","roll","pitch","yaw"],
    "left":  [[100, 210, 206, 296, 82, 0.3, 0.2, 2.2], ...],
    "right": [[100, 198, 211, 288, 91, -0.4, 0.1, 1.8], ...]
  }
}
```

- `t`는 **세션 시작 기준 ms 오프셋**입니다. 좌우가 같은 축이라 그대로 겹쳐 볼 수 있습니다.
- `fsr1..4`는 **물리 CH1–CH4 순서**입니다. 해부학적 위치는 drill/capture의 `channels` 배열과 명시적으로 대응합니다 (`["P6","P3","P2","P1"]`이면 CH1=P6, CH2=P3, CH3=P2, CH4=P1).
- 발당 12,000샘플(10Hz 20분) 상한. 초과 시 `rawTruncated: true`.
- CONFIG → 기록 → 원시 샘플 기록 에서 끌 수 있습니다.

**보행 데이터를 모으려면** 아무 drill이나 실행한 채로 걸으면 됩니다 — 판정 결과와 무관하게 원시 스트림은 그대로 기록됩니다.

**데이터를 꺼내려면** LOG → 내보내기 (JSON). API 키는 백업에 포함되지 않습니다.
저장 공간이 부족하면 오래된 원시 블록부터 자동으로 버리고, 집계값·기록 폼·리포트는 항상 보존합니다.

## 동작 캡처 (v2.5–2.6)

판정 없이 연속 구간을 기록하고, 그중 좋은 구간만 잘라 훈련 기준으로 쓰는 경로입니다.

```
LIVE → 🎬 MOTION CAPTURE (연속 기록)
  라벨 입력 → ● REC (3초 카운트인) → 걷기/동작
  [구간 표시] 로 좋은 순간에 마커를 꽂음
  ■ STOP → 라벨 #테이크 로 저장   (10분/발당 6,200샘플에서 자동 종료)

테이크 탭 → 파형 상세
  마커 칩 = 시작점 스냅 (길게 눌러 끝점)
  시작/끝 슬라이더로 구간 조절 — 선택 밖은 어둡게 표시
  [선택 구간 저장]  → 잘라낸 구간을 새 캡처로 (t는 0부터 재기준)
  [기준값으로 →]   → 구간의 채널별 최대값으로 CONFIG 드릴 마법사 진입
```

캡처는 세션과 별도 저장소(`onyxSDI_captures`)에 들어갑니다. drill·정확도·리포트가 없어서
세션 배열에 섞으면 LOG 누적 통계와 조교 피드가 오염되기 때문입니다.
LOG → 내보내기에는 세션·동작과 함께 실려 나갑니다.

캡처 JSON:

```jsonc
{
  "captureId": "c_20260905_00123",
  "label": "보행", "take": 3,
  "hz": 10, "duration": 12.4,
  "fields": ["t","fsr1","fsr2","fsr3","fsr4","roll","pitch","yaw"],
  "feet": ["left","right"],
  "markers": [{ "t": 4200 }],
  "trimmedFrom": "c_20260905_00119",   // 잘라낸 구간이면 원본 id
  "left":  [[0, 210, 206, 296, 82, 0.3, 0.2, 2.2], ...],
  "right": [[0, 198, 211, 288, 91, -0.4, 0.1, 1.8], ...]
}
```

파형은 구간별 min/max로 줄여 그립니다 — 평균으로 줄이면 접지 봉우리가 뭉개져
어디를 잘라야 할지 눈으로 찾을 수 없습니다 (`decimate()` in `js/tabs/live.js`).

> **현장 주의** — 녹화 중 화면이 꺼지거나 앱이 백그라운드로 가면 브라우저가 타이머를
> 조일 수 있습니다. 캡처 중에는 화면을 켜둔 채로 두고, 첫 테이크는 짧게 찍어
> 샘플 수가 `길이 × 10` 근처인지 확인하세요.

### 영점(BASELINE)과 판정 단위 (v2.9)

신발을 신으면 아무것도 밟지 않아도 FSR이 700~800을 찍습니다. 그 장착 압력을
빼지 않고 임계값과 비교하면 positive 압점은 영원히 충족되고 negative 압점은
매 샘플 경보를 냅니다. 그래서 v2.9부터는 이렇게 동작합니다.

- **훈련도 영점을 먼저 잽니다.** TRAINING에서 고른 drill은 BASELINE을 측정하기
  전에는 시작할 수 없습니다. 판정은 `sample - baseline`으로만 이루어집니다.
- **임계값·기준값·정확도·보행 활성 기준·좌우 균형이 모두 같은 단위**입니다.
  세션 로그는 schema 4이고 `units: 'delta'`와 사용한 baseline을 함께 남깁니다.
  원시 블록은 손대지 않은 raw이므로 나중에 다시 판정할 수 있습니다.
- **절대 임계값은 좌우가 따로입니다** (`thr: { left, right }`). 두 유닛은 서로
  다른 신발에 들어간 별개 기구라 장착 압력이 다릅니다. v2.9 이전 drill의 숫자
  하나는 양발에 그대로 복사되므로 기존 동작은 바뀌지 않습니다.
- **BASELINE 게이트는 두 갈래입니다.** 수신 부족·공백·측정 중 연결 변경은
  막습니다(중앙값 자체를 못 믿습니다). 흔들림 폭과 센서 상한 고정은 측정값을
  그대로 보여준 뒤, 사유를 한 줄 남기면 진행할 수 있습니다.
- **모든 시도가 기록됩니다.** 통과·미통과를 가리지 않고 채널별 기준값·흔들림·
  남은 범위·수신율과 3초치 원시 샘플을 남기고, BASELINE 화면에서 JSON으로
  내보냅니다.
- **흔들림 한계는 착용 상태별 설정값입니다.** `⋮ → 🛠 개발 도구 → BASELINE
  흔들림 한계`에서 맨발과 신발 착용을 따로 넣습니다. 둘 다 35에서 출발하지만
  35는 맨발 기준으로 정해진 값이라 신발 쪽은 재보고 정해야 합니다.

#### 신발 착용 한계값을 정하는 순서

```
펌웨어 v2.9 업로드 → 신발 신고 baseline 10회 이상 → 기록 내보내기
  → node tools/baseline-limit.cjs <파일> → 개발 도구에 입력
```

스크립트는 착용 상태별 흔들림 분포, 채널별 중앙값, 후보 한계마다 지금까지의
측정 중 몇 퍼센트가 걸렸을지를 찍습니다. 한 채널만 계속 크면 한계값이 아니라
그 채널의 장착을 고쳐야 합니다. 권장값은 채널 p90을 5 단위로 올린 값이고,
고르는 것은 사람이 합니다. 펌웨어를 올리기 전에 모은 기록은 숫자가 달라지므로
쓰지 마세요.

### 압점 배치·baseline·보행 분석 (v2.7 준비)

FREE CAPTURE와 MOTION CAPTURE는 모두 촬영 전에 다음 순서를 거칩니다.

```
FSR 배치 4곳 직접 선택(CH1 → CH4 순서) → 장비 착용 → 3초 BASELINE → 촬영
```

- 발바닥 후보 위치는 P1–P12이며, 보행/정적 균형/아치/후족부 프리셋을 제공합니다.
- FREE/MOTION 모두 시작할 때 선택이 비어 있으며, 4곳을 직접 누르거나 프리셋을 명시적으로 골라야 다음 단계로 이동합니다.
- baseline은 한 샘플이 아니라 3초 동안 받은 값의 채널별 중앙값입니다.
- 저장 파일에는 원본 raw와 baseline을 모두 남기고, 화면·분석만 `max(0, raw-baseline)`을 씁니다.
- 압점은 baseline 대비 3 이상 변하면 파랑으로 켜지고, 이후 초록→노랑→주황→빨강으로 표시됩니다. 신발로 센서가 상한에 가까워도 값이 고정되지 않고 변하면 측정을 계속할 수 있습니다.
- MOTION CAPTURE 중 좌/우, 전족/후족 균형과 4점 기반 상대 COP를 표시합니다.
- 저장 후 힐 채널 상승 에지(히스테리시스, 최소 300ms)로 스텝을 나누고, 0–100% 정규화 오버레이를 표시합니다.

`COP`와 스텝 검출은 4개 센서로 계산한 상대 추정치입니다. 절대적인 임상 압력중심으로 해석하지 말고 동일 착용자의 반복 측정 비교에 사용하세요.

벨크로 도착 후 하드웨어 확인 순서: 한쪽씩 CH1–CH4 탭 테스트 → 양발 baseline 반복성 → 10초 보행 3회 → 샘플 수(약 10Hz)와 스텝 수 대조 → 센서 위치를 바꿔 프리셋 매핑 검증.

### 펌웨어 v2.9

FSR을 채널당 5회 읽어 중앙값을 보내고, ADC 획득 시간을 3µs에서 10µs로
올렸습니다. 전송 규약·10Hz 주기·IMU 필터는 그대로입니다. 순수 ADC 잡음만
놓고 보면 3초 구간의 흔들림 폭이 대략 절반으로 줄고, 발이 실제로 움직여서
생긴 폭은 줄지 않습니다. 올린 뒤에는 **양발 baseline과 등록된 drill의
기준값을 모두 다시 잡으세요** — 같은 하중에서 읽히는 숫자가 조금 달라집니다.

## 로컬 실행

빌드 과정이 없습니다. 정적 파일을 그대로 서빙하면 됩니다.

```bash
python -m http.server 8123
```

`http://localhost:8123` 접속. Web Bluetooth는 보안 컨텍스트를 요구하므로 `localhost` 또는 HTTPS여야 합니다.

캐시가 말썽이면 URL에 `?nosw=1`을 붙이세요 — Service Worker를 등록하지 않고 캐시를 전부 지웁니다.
자세한 운영 절차는 [DEPLOY.md](DEPLOY.md)에 있습니다.

## 구조

```
index.html          단일 페이지, 탭 4개
js/
  bluetooth.js      BLE 전송 계층 — 발마다 독립된 link 인스턴스
  session.js        세션 상태와 판정
  store.js          localStorage 영속화
  pwa.js / sw.js    Service Worker 등록과 캐시 무효화
  tabs/             live · training · config · log
css/                토큰 기반 테마 (다크/라이트)
```

버전을 올릴 때는 `python bump-version.py <버전>`을 쓰세요.
`js/version.js`와 `index.html`의 모든 `?v=`를 동시에 갱신해서 캐시를 확실히 무효화합니다.
